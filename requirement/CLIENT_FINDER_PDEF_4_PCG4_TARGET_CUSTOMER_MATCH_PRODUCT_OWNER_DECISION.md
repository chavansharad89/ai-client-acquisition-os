## 3. Repository evidence

**Option A (Search-membership implies match).** `packages/core-search/src/pgRepository.ts` stores and returns
`target_customer` as a column on the `searches` table (`COLUMNS` includes `target_customer`; `createSearch`
writes `input.parameters.targetCustomer`; `findById`/read paths return `targetCustomer: row.target_customer`).
Nothing in `pgRepository.ts` or `types.ts` filters, scores, or records anything about a *specific discovered
business's* characteristics — `target_customer` is written once, at Search creation, from the user's own stated
criterion, and is never written to or compared against from the Search side again. The actual prospect-matching
work (if any) happens in `@acos/core-discovery`, which is outside `core-search` and is, per the preparation
record's own framing (§7.1, not reopened here), a *candidate* filter that decides who gets researched — not an
observed-match determination. Confirmed directly: Search membership encodes only the query-side criterion, never
an observed characteristic of the resulting Opportunity's Prospect. **Option A is not honestly selectable** —
treating "discovered under this Search" as "confirmed target-customer match" would require asserting that
Discovery's candidate filter is infallible, which no code or governing record establishes, and would functionally
re-derive a category-plausibility-shaped substitution that B-3's own Qualification-equivalence-evaluator inputs
decision (`CLIENT_FINDER_PDEF_4_ENGINEERING_BLOCKER_DECISION.md` §8, "Inputs: (a) the Search row's immutable
criteria snapshot plus the Opportunity's own attributes only") does not supply a basis for, since it is Search
*criteria*, not a Discovery outcome, that B-3 names as an input.

**Option C (name a specific existing signal).** Surveyed candidates, each checked against its actual definition
rather than its name:
- Category-plausibility (`@acos/core-research`'s `getCategoryPlausibilityDetermination`) — explicitly excluded by
  the governing B-3 record's own text (quoted in the preparation record §6: "do NOT use category-plausibility as a
  substitute; B-3 explicitly excludes that"). Confirmed not reopened.
- `StoredResearchSignal` (`@acos/core-research`) — not excluded by name, but no governing record (B-3, ED-10, or
  this preparation record) affirmatively permits research signals as evaluator input, and the 2026-10-05 PO ruling
  quoted in the preparation record directs against using them absent such explicit permission. No permission found
  in any file read for this decision.
- `Opportunity.offer_rationale` — free text generated by `suggestOffers()`; not a structured target-customer
  field; using it would require inventing new parsing/derivation logic, which this decision is barred from doing.
- `Opportunity`/`Prospect`/`Company` schema (migration `0017_opportunities`) — confirmed by direct reading: no
  `target_customer`, `observed_target_customer`, or equivalent column exists anywhere in this schema.
**No existing field or signal in the repository, examined on its actual definition, satisfies B-3's requirement of
an input drawn from "the Search row's immutable criteria snapshot plus the Opportunity's own attributes" that
independently records an *observed* target-customer characteristic. Option C is not honestly selectable** — not
because no candidate was proposed, but because every proposed candidate either is explicitly excluded (category
plausibility) or lacks the authorization/structure B-3 requires (research signals, free text, absent schema).

**Option B (new field).** Confirmed: no schema change, migration, or pipeline stage currently exists that would
populate an Opportunity-level observed-target-customer signal. This is new, unauthorized-until-now engineering
scope, consistent with the preparation record's own framing.

**Option D (accept permanent UNKNOWN).** Confirmed via `CLIENT_FINDER_PDEF_4_LAUNCH_CRITERIA_DECISION.md` §6.3–
§6.4: PCG-4 is explicitly classified as a MONITORING/OPTIMIZATION gate, not one of the four hard launch blockers
(PCG-1, PCG-2, PCG-3A, PCG-3B). Confirmed via `CLIENT_FINDER_PDEF_4_IMPLEMENTATION_CONFORMANCE_RECORD.md` §3/§12:
PCG-4 is already running today as `NOT YET EVALUABLE`/numerator-structurally-zero, and this is documented as
correct, intended, fail-soft behavior, not a defect. Selecting D would not change current runtime behavior at all
— it would only make explicit, by Product Owner act, that this behavior is accepted rather than pending.

## 6. Product Owner rationale

Option A and Option C are ruled out on the evidence in §3, not by default avoidance: A collapses to treating a
query-side criterion as a confirmed observation, which no code supports and which the governing B-3 and category-
plausibility-exclusion records would treat as an unauthorized substitution; C has no genuine candidate once each
proposed signal is checked against its actual definition rather than its name. With A and C both foreclosed by
evidence, the only remaining choice is between B (define new scope that can eventually make the criterion
genuinely evaluable) and D (accept permanent non-evaluability now).

B is selected over D because `TARGET_CUSTOMER_MATCH` is a specifically named, product-meaningful sub-part of the
"useful outcome" concept (per the Implementation Authorization record's own "target customer criteria" language
and B-7's conjunctive combination logic) — it is not a nice-to-have metric but one third of the stated
qualification-equivalence contract. Declaring it permanently `UNKNOWN` by product choice (D) would be a durable
statement that this project does not intend to ever measure whether a discovered Opportunity's actual target-
customer characteristics were observed to match the user's criterion — a significant, permanent narrowing of
PCG-4's intended meaning. Because PCG-4 is a monitoring-only gate (§3, confirmed), choosing B carries no launch
risk or urgency pressure; there is no reason to foreclose future measurement permanently when the correct,
evidence-grounded answer is that the signal simply does not exist *yet*, not that it cannot exist. B preserves the
option to build it later without requiring a fresh Product Owner reconsideration of the semantics once engineering
capacity exists, while D would require a future Product Owner act to reopen a question this record can resolve
now by defining, at the product level, exactly what a future implementation would need to produce.

## 7. Exact semantics of `TARGET_CUSTOMER_MATCH` after this decision

`TARGET_CUSTOMER_MATCH` continues to mean, precisely: *whether the specific Opportunity's Prospect, as actually
observed during research/review, was found to be the kind of customer the user's Search configured as its
`targetCustomer` criterion* — a statement about the Prospect's own observed characteristics, never about:
- the user's configured `targetCustomer` criterion alone (that is the Search's input, not the Opportunity's
  observed output);
- Search or Discovery membership (a candidate filter, not a confirmed observation);
- service match, minimum-value match, or category plausibility (each a distinct, separately defined criterion or
  mechanism, per §6 of the preparation record, not reopened);
- any free-text, prose-derived, or inferred characterization not backed by a structured field.

Until a future, separately authorized engineering-design and implementation stage populates an
observed-target-customer signal satisfying this definition, `TARGET_CUSTOMER_MATCH` correctly resolves to
`'UNKNOWN'` for every Opportunity, exactly as implemented today.

## 9. Downstream engineering implications

The exact dependency handed to a future implementation-authorization step, stated at the product-semantics level
only (no migration, field name, table, or pipeline design is performed here):

- A new signal must exist that answers exactly one question, for a given Opportunity: *"Was this Opportunity's
  Prospect, as actually observed (not merely as filtered-for at Discovery time), found to match the user's
  configured `targetCustomer` criterion?"* — with a tri-state result (match / no-match / not-yet-observed), not a
  boolean, so that an Opportunity not yet reviewed for this characteristic can still resolve to `'UNKNOWN'` under
  `evaluateTargetCustomerMatch`'s existing fail-soft contract rather than a default `true` or `false`.
- The signal must be populated by some observation/review stage of the pipeline (not Discovery's candidate filter,
  per §3's Option-A finding, and not category-plausibility, per the already-governing B-3 exclusion) — which stage,
  and how it is triggered, is explicitly left to a future engineering-design decision, not decided here.
- Once such a field exists, the minimum wiring change (not performed here) is: add the new field to
  `QualificationEquivalenceSubject`'s construction in `packages/core-launch-gates/src/pcg4.ts` (replacing the
  current hardcoded `observedTargetCustomer: null`), with no change required to
  `evaluateTargetCustomerMatch`/`rules.ts` itself, since its contract already expects exactly this shape of input.

This is new engineering scope requiring its own ED-series and implementation-authorization decisions before any
code, schema, or migration work begins.
