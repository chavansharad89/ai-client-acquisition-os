# PART 4 — REMAINING ENGINEERING READINESS ITEMS

## 4.1 Entity / IdentityEvidence DDL (implementation-ready schema specification, no migration created)

Column types, nullability conventions, and id/timestamp patterns below follow the repository's own existing convention exactly, verified directly against `packages/db/prisma/migrations/0015_discovery/migration.sql` (`TEXT` ids, `TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP`, `TEXT ... CHECK (... IN (...))` for enumerated state, never a native Postgres enum type) and `0045_research_signal_cache_index`.

### `entities`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `TEXT` | No | PK. Generated by application code (`randomUUID()`, matching `leadUnlockRepository.ts`'s convention), never derived from name/domain/phone/provider ID (D1). |
| `created_at` | `TIMESTAMP(3)` | No | `DEFAULT CURRENT_TIMESTAMP`. |

- **Primary key:** `id`.
- **Foreign keys:** none — `entities` is the root of this layer, `user_id`-free (D8).
- **Indexes:** none beyond the primary key; `entities` is looked up only via `identity_evidence`, never scanned directly.
- **Uniqueness:** none beyond PK — there is deliberately no uniqueness constraint derived from any business attribute, since D1 forbids deriving identity from one.
- **CHECK constraints:** none.
- **Append-only / delete behavior:** no `UPDATE` or `DELETE` path is ever issued against this table by application code (D10: permanent ID, no delete). No `status` column exists on `entities` itself — Entity Status is a derived read over `entity_status_evidence` (§4.1 below), never a mutable column here, consistent with `ENGINEERING_SPECIFICATION_FINAL.md` §6 ("status is a *derived* read, not a stored mutable column").

### `identity_evidence`

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `TEXT` | No | PK. |
| `entity_id` | `TEXT` | No | FK → `entities.id`. |
| `category` | `TEXT` | No | `CHECK (category IN ('PROVIDER_STABLE_ID','OFFICIAL_DIGITAL_IDENTITY','VERIFIED_CONTACT','WEAK_SUPPORTING'))` — the four D22 categories, named explicitly so a fifth cannot be silently introduced by a typo. |
| `evidence_type` | `TEXT` | No | E.g. `'GOOGLE_PLACE_ID'`, `'DOMAIN'`, `'OFFICIAL_PROFILE_URL'`, `'VERIFIED_PHONE'`, `'VERIFIED_BUSINESS_EMAIL'`. Distinct from `category` because one category may admit more than one concrete evidence type (D22 Category 2 covers both domain and official profile URL). |
| `normalized_value` | `TEXT` | No | The comparison key — exact-match string per `ENGINEERING_SPECIFICATION.md` §3 (byte-exact for Place ID; normalized-domain exact-match for domain; scheme+host+path normalization for profile URL). |
| `source_provider` | `TEXT` | No | E.g. `'GOOGLE_PLACES'`. Scopes `normalized_value` comparisons to the same provider namespace (D1/§3: "a Place ID from one provider namespace must never be compared against another provider's ID space"). |
| `verified` | `BOOLEAN` | No | `DEFAULT false`. Set per D23's test (a reliable source directly associates the value with the Entity); OQ-4 already decides `websiteUri` satisfies this without DNS/owner proof. |
| `observed_at` | `TIMESTAMP(3)` | No | D11 append-only observation timestamp. |
| `discovery_event_id` | `TEXT` | Yes | FK → `discovery_events.id`. Nullable because an evidence row's originating `DiscoveryEvent` may not always be the natural owner of record for every future producer (e.g. a hypothetical future non-discovery producer); nullable, not forced, to avoid inventing a requirement D21 does not state. |
| `conflict_state` | `TEXT` | No | `CHECK (conflict_state IN ('NONE','CONFLICTED'))`, `DEFAULT 'NONE'`. Set to `'CONFLICTED'` per OQ-3 when two existing Entities' strong anchors disagree; never deleted, never silently cleared (D11/D18 append-only). |

- **Primary key:** `id`.
- **Foreign keys:** `entity_id → entities.id` (`ON DELETE` intentionally **not** `CASCADE` — D10 forbids Entity deletion, so no delete path should ever reach this FK in practice; specify `RESTRICT` to make an accidental delete attempt fail loudly rather than silently cascade). `discovery_event_id → discovery_events.id`, `ON DELETE SET NULL` is inappropriate since `discovery_events` is also immutable/non-deleted (D10/D21) — specify `RESTRICT` here too, for the same reason.
- **Indexes:** `(entity_id)` — every resolver read is "find evidence for this Entity" or "find Entities matching this evidence," never a scan without one of these two access patterns.
- **Uniqueness (the two partial unique indexes D13/OQ-1 require):**
  - `UNIQUE (source_provider, normalized_value) WHERE category = 'PROVIDER_STABLE_ID'` — this is what makes Place ID collision a constraint violation (surfaced to the resolver as the conflict case, OQ-3) rather than a silent duplicate, and what the transaction-wrapper's retry logic (§4.2) relies on for concurrency safety.
  - `UNIQUE (source_provider, normalized_value) WHERE category IN ('OFFICIAL_DIGITAL_IDENTITY','VERIFIED_CONTACT')` — same mechanism for domain/profile-URL/phone/business-email anchors, scoped per provider namespace. **Deliberately no unique index for `category = 'WEAK_SUPPORTING'`** — D12 forbids Category 4 from participating in resolution at all; a uniqueness constraint on it would silently grant it resolution power the PO decisions never authorize.
- **CHECK constraints:** `category`, `conflict_state` as above.
- **Append-only / delete behavior:** no `UPDATE` path rewrites `normalized_value`/`category`/`evidence_type`/`verified` once written (D11). The only legitimate `UPDATE` is to `conflict_state`, from `'NONE'` to `'CONFLICTED'` — never the reverse, and this is the one narrow, explicitly-D13/D18-sanctioned mutation this table permits; it is not a general-purpose mutable table.

## 4.2 Transaction wrapper (exact specification, no implementation)

**Idiom reused, verified directly:** `packages/core-subscriptions/src/leadUnlockRepository.ts:96-149`'s `revealAtomically` — `pool.connect()` → `client.query('BEGIN')` → sequential statements on the same `client` → `client.query('COMMIT')` → `catch` block issuing `client.query('ROLLBACK').catch(() => undefined)` and re-throwing a domain-specific error → `finally { client.release() }`. No new transaction mechanism, no ORM-level transaction helper, no distributed-transaction library is introduced — this wrapper is the same idiom, applied to a different set of statements.

**Exact transaction boundary — what is inside the `BEGIN`/`COMMIT`, for one candidate:**
1. Resolver read: query `identity_evidence` for any row matching the candidate's available Category 1–3 evidence (Place ID exact-match; domain/profile-URL/phone/email exact-match, each scoped to its own provider namespace).
2. Based on the read: either (a) no match → insert a new `entities` row plus its `identity_evidence` row(s) (`NO_MATCH_NEW_ENTITY`), (b) exactly one match satisfying OQ-1/OQ-2 → reuse that `entity_id` (`DEFINITE_MATCH`), or (c) matches on two different existing Entities → `UPDATE identity_evidence SET conflict_state = 'CONFLICTED'` on both existing Entities' matching rows, then insert a new `entities` row for the triggering discovery (OQ-3).
3. Insert the `discovery_events` row, carrying whichever `entity_id` step 2 produced.
4. The existing Company upsert (`pgRepository.ts`'s `ON CONFLICT` statement), now additionally carrying `entity_id`.
5. The existing Prospect upsert, unchanged.

**Inputs:** one `DiscoveryCandidate` (post-normalization) plus its available identity-evidence fields (Place ID, normalized domain), the `userId`, the `searchId`, and the current timestamp — the same inputs `runDiscoveryForOwner`'s existing per-candidate loop iteration already has in scope.

**Outputs:** the committed `{ company, prospect }` pair (unchanged shape from today), plus the resolved `entity_id` now present on `company`. On rollback, no output — the candidate is treated exactly as today's `skipped` outcome, logged under a distinct reason (DB failure, not normalization rejection).

**Rollback behavior:** any error at any step inside the boundary issues `ROLLBACK`; none of steps 1–5 is partially visible outside the transaction. This specifically prevents an orphaned `entities`/`identity_evidence`/`discovery_events` row with no corresponding Company/Prospect.

**Retry behavior:** not automatic within the wrapper itself. A caller-level retry (if ever added) would simply re-run the whole candidate through a fresh transaction; because `discovery_events` has no uniqueness constraint (D21 sanctions duplicates), a retry after a crash may produce a second `discovery_events` row for what was actually one real attempt — an accepted, named consequence, not a defect, exactly as `ENGINEERING_SPECIFICATION_FINAL.md` Q2 states.

**Concurrency behavior:** ordinary Postgres `READ COMMITTED` (the existing default, not changed). Two concurrent transactions resolving the same Place ID: the second transaction's step-1 read either sees the first's already-committed `identity_evidence` row (if the first committed first) and correctly produces `DEFINITE_MATCH`, or — in the genuine race case where both transactions' step-1 reads miss each other — both attempt to insert a new `identity_evidence` row with the same `(source_provider, normalized_value)` under `category = 'PROVIDER_STABLE_ID'`; the partial unique index from §4.1 causes the second commit to fail with a unique-violation, which the wrapper's `catch` surfaces as a retriable error (not a silent duplicate Entity) — this is the exact mechanism, not merely the intention, that prevents two Entities for the same Place ID under concurrent discovery.

**Unique constraint behavior:** a unique-violation during step 2 is the *expected* signal path for the race case above, not an unexpected failure — the wrapper's error handling must distinguish "unique violation on the Place-ID partial index" (retriable: re-read and treat as `DEFINITE_MATCH` against the now-committed winner) from any other DB error (not retriable by this wrapper; surfaces as a failed candidate, same as today's DB-failure path).

**Per-candidate, not per-batch:** one transaction per candidate, matching today's per-candidate loop structure in `runDiscoveryForOwner` — never one long-held transaction spanning an entire discovery run's candidate list.

## 4.3 `normalizeCandidate()` caller / nullability audit (traced this pass, not assumed)

**Exact current behavior, re-confirmed:** `packages/core-discovery/src/normalize.ts:43-51` — `normalizeCandidate()` returns `null` if `candidate.name` is falsy, or if `normalizeDomain(candidate.website)` returns falsy; otherwise returns `{ name, normalizedDomain: string }` (non-nullable field on `NormalizedCandidate` today).

**Every production caller, found by repository-wide search (two, not one — the prior audit chain documented only the first):**

1. **`packages/core-discovery/src/service.ts:126`** (`runDiscoveryForOwner`). On `null`, increments a `skipped` counter and `continue`s the loop — **already null-safe at the call site**. This caller requires no change to tolerate `normalizeCandidate()` returning `null` more often once C-1 relaxes the website-required branch; it already handles `null` today for the "missing name" case.

2. **`apps/worker/src/searchWorker/intentIntake.ts:107`** (`recordIntentIntakeForOwner`, the Client Intent Discovery / K1-adjacent intake path — **not previously enumerated in any prior audit in this chain**). On `null`, throws `IntentSignalValidationError('website', 'invalid', ...)` — **this caller treats a missing/unparseable website as a hard validation error for *this specific path*, not as a silently-skipped candidate.** This is a deliberate, existing design choice independent of C-1 (the comment at line 112 reads "intent intake does not invent company identity") and is **out of scope for C-1's website-less discovery fix** — intent intake is a trusted, authorization-evidence-gated path (OD-13/K1), not the open discovery pipeline C-1 governs. **This caller must not be silently changed** by a future C-1 implementation; C-1's relaxation applies to `runDiscoveryForOwner` (open discovery), not to `recordIntentIntakeForOwner` (authorized intake), and a future implementer must preserve this distinction explicitly rather than assume both call sites should change together.

**Downstream consumers of `NormalizedCandidate.normalizedDomain` / `company.normalizedDomain`, traced from `normalizedDomain`'s actual type (`string`, today) to every place that type is propagated — this is the caller-nullability audit the prior readiness audit flagged as outstanding, performed here:**

| Consumer | File | Behavior if `normalizedDomain`/`company.normalizedDomain` becomes `string | null` |
|---|---|---|
| Company upsert `INSERT` | `packages/core-discovery/src/pgRepository.ts:41-46` | **Breaks today's `NOT NULL` column constraint** if passed `null` without the §4.1 `companies.normalized_domain` nullability migration landing first — this is exactly why that migration (M6-equivalent) must land no later than, not after, this code path is exercised with a null domain. Already identified; re-confirmed here as the first hard dependency. |
| `ON CONFLICT (user_id, normalized_domain)` upsert target | `pgRepository.ts:43` | **A `NULL`-domain row can never hit this conflict target** (ordinary Postgres NULL semantics: no two NULLs are "equal" for a unique index unless a partial index is used). A second website-less discovery for the same user does **not** dedupe against the first via this statement — confirming, independently, the exact gap `ENGINEERING_SPECIFICATION.md` §8 already named: domain-based dedup structurally cannot cover website-less companies; Entity-resolver-based dedup (via `identity_evidence`, §4.1) is the only mechanism that can, and only when Category 1–3 evidence is actually present (Cases F/G/H of §7 of the original engineering specification remain genuinely non-deduplicated even after this change — a known, accepted consequence, not newly discovered here). |
| Research input assembly | `packages/core-research/src/service.ts:184` (`normalizedDomain: company.normalizedDomain`) | Propagates whatever type `company.normalizedDomain` has into `LeadResearchInput.normalizedDomain` (`provider.ts:15`, currently `string`, non-nullable). **This type must become `string | null` too, or this call site fails type-checking the moment `company.normalizedDomain` is nullable** — a change not previously enumerated in any prior document in this chain. |
| Signal cache read/write | `packages/core-research/src/service.ts:199`, `signalCache.ts:19,37`, `pgRepository.ts:181` (core-research) | All key on `normalizedDomain: string` today. **A `null` domain cannot be used as a cache key under the existing `(user_id, normalized_domain, signal_kind)` scheme** — the correct behavior is to skip caching entirely for a null-domain prospect (never cache under a sentinel string like `''`, which would incorrectly conflate every website-less company for one user into a single cache entry), not to silently coerce `null` into a cache-key string. |
| **Source document fetch — the most consequential downstream dependency, not previously named in any prior audit in this chain** | `packages/core-research/src/sourceDocumentProvider.ts:177` (`` `https://${target.normalizedDomain}` ``), `anthropicResearchProvider.ts:79`, `fallbackResearchProvider.ts:104` (both `` `https://${input.normalizedDomain}` ``) | **These construct the literal URL fetched for research.** If `normalizedDomain` is `null`, the current code would construct the literal string `"https://null"` and attempt to fetch it — a silent, incorrect behavior, not a crash, which is worse. **This is the single most important finding of this caller audit: a website-less company has no homepage for the research pipeline to fetch, structurally, regardless of Entity identity.** The correct behavior, which must be specified before C-1 ships for any candidate that also reaches research, is: when `company.normalizedDomain IS NULL`, the research pipeline must skip source-document fetch and homepage-dependent fields entirely for that Prospect (equivalent to today's "fetch failure → resolves to `[]`" path in `sourceDocumentProvider.ts`, reused rather than reinvented) — **never** construct a URL from a null domain. This is a necessary, specific consequence of C-1 that no prior document in this chain enumerated; it does not change any PO decision (C-3B already permits AI-optional/no-signal outcomes), but it is a concrete implementation requirement this audit surfaces for the first time. |
| `apps/worker/src/searchWorker/worker.ts:485, 605` | Passes `company.normalizedDomain` into the same research-input-assembly and cache-key call sites above | No additional distinct consumer beyond what the two rows above already cover — re-confirmed, not a new call site requiring separate treatment. |

**Conclusion of this audit:** Items 1–3 of the implementation-readiness audit's §6 list (relax `normalize.ts`, migrate `companies.normalized_domain` to nullable, adjust the `ON CONFLICT` target's practical effect) were already correctly identified as bounded. **Item 4 (the caller audit) was not merely "unenumerated" — it surfaces one previously-unidentified production caller (`intentIntake.ts`) that must be deliberately excluded from C-1's relaxation, and one previously-unidentified hard dependency (the research pipeline's source-document fetch, which literally cannot function without a domain) that must fail safe, not merely be type-checked.** Both are now bounded and specifiable; neither requires further PO input — they are engineering specification, consistent with every prior document's classification of this item.
