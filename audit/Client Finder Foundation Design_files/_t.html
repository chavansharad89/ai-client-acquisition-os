A

Final identity decision

Adopt IDENTITY ≠ ENTITLEMENT ≠ PAYMENT. Repository evidence not only permits it — the code already implements it.

resolveAccess is two independent steps, and only the second touches entitlements:

// 1. IDENTITY — consults the token row alone
const stored  = await repository.findAccessToken(hashAccessToken(rawToken));
const verdict = evaluateAccessToken(stored, now);   // existence · revoked · expired
if (!verdict.valid) return { granted: false, … };

// 2. ENTITLEMENT — a separate lookup, a separate concern
const entitlements = await repository.listActive(normaliseEmail(verdict.customerEmail));
return { granted: true, context: { …, purchased }, … };

evaluateAccessToken returns an identity without reading a single entitlement, and granted: true is returned even when purchased is empty. A valid token already means “we know who you are”, not “you have bought something”.

The two couplings to remove

CouplingWhereChange
Identity keyed on email, not an opaque idaccess_tokens.customer_emailAdd nullable user_id; email stays for existing entitlement tokens
Token issuance gated on owning somethingreissue.ts:88 — if (entitlements.length === 0)Leave it. That function issues an entitlement credential and should keep its gate. Session issuance is a separate function with no such gate.

Minimum schema and code boundary

IDENTITY users(id, email, name, …) access_tokens(user_id → users.id) ← session when user_id IS NOT NULL resolveSession(token) → userId ← new; wraps evaluateAccessToken FEATURE users.client_finder_enabled_at ← nullable timestamp requireClientFinder(userId) → void|throw ← new ENTITLEMENT entitlements(customer_email, product_slug, order_id) ← unchanged resolveAccess(token) → purchased[] ← unchanged PAYMENT orders → payments ← unchanged, untouched

One credential table, two credential kinds, distinguished by whether user_id is null. Same minting, same hash-only storage, same revocation, same expiry evaluation — all of it already written and tested.

Provisioning without email infrastructure

An operator-run provisioning script, not a signup flow. It inserts a users row, calls the existing mintAccessToken(), stores the hash with user_id set, and prints the plaintext token once to the operator's terminal. The operator hands that link to the validator out of band.
  • No email transport, no SMTP credential, no deliverability problem.
  • Reuses the exact issuance path magic-link will later use.
  • Appropriate to the controlled scenario — one service, one city, a known handful of validators.
Magic-link later requires no redesign of Client Finder ownership. Ownership is anchored on users.id, which is independent of how that row came to exist. Adding magic-link adds a login route that calls the same issuance and sets the same cookie. Every user_id foreign key, every repository filter and every ownership test is unaffected.
B

Final entitlement decision

Existing architecture makes the separation unavoidable — this is not a preference. entitlements.order_id is TEXT NOT NULL with a foreign key to orders. There is no way to express “this user may use Client Finder” in that table without either fabricating an order or making order_id nullable — and the column exists specifically so support can answer “why does this person have access?”. Weakening it to model a non-purchased grant would damage a payment invariant to solve an identity problem.

Minimum entitlement boundary

QuestionAnswered byMechanismNew?
Who is this?Sessionaccess_tokens.user_id → users.idColumn
May they use Client Finder?Feature accessusers.client_finder_enabled_at IS NOT NULLColumn
What have they bought?Entitlemententitlements.product_slugExists
What did they pay?Payment historyorders → paymentsExists

A nullable timestamp, not a boolean: it records when access was granted at identical cost, which is the difference between an auditable grant and a flag nobody can explain later. Not a feature_grants table — a table for one column at MVP scale is scope expansion, and §8 of the Scope Boundary answers no, no, no, yes to it.

Convergence path, if Client Finder later becomes the ₹1,499 product. A grant service sets client_finder_enabled_at when a matching entitlement appears, and clears it on revocation. No table changes, no ownership changes — the authorization check requireClientFinder() keeps reading the same column. The two concepts stay separate; one merely becomes the other's cause.

Not hard-coded, as instructed: nothing in the design equates a paid ₹1,499 customer with a user identity. A user may exist with no entitlement, an entitlement may exist with no user (every current row), and both remain true after this change.

C

Final ServiceProfile

The Scope Boundary's four fields cannot drive the existing offer engine. This is the “verified Client Finder dependency” exception, found by inspecting the consumer rather than the PRD. suggestOffers(signals, rules) takes ServiceRule[], and that interface requires five fields: 
export interface ServiceRule {
  service: string;
  triggers: readonly ResearchSignal['kind'][];   // which signal kinds fire this
  keywords: readonly string[];                   // substrings that strengthen the match
  typicalValuePaise: number;                     // engagement value
  rationale: string;                             // '{signal}' template
}
Without triggers, keywords and rationale the engine cannot match a signal to an offer, and every user falls back to DEFAULT_SERVICE_RULES — which is exactly the defect the Readiness Audit recorded as PF-01.

Sub-decision — typicalValuePaise. Semantically it differs from minProjectValuePaise: typical is what an engagement is worth (it populates Opportunity.estimatedValuePaise); minimum is the user's floor. For the MVP, deriving typical := minProjectValuePaise is a defensible simplification that removes a field the user would have to guess at. Recommended, but flagged — it makes every opportunity's estimated value equal to the user's floor, which may read oddly in the UI.

Resolution of the conflict: seven fields, not four and not thirteen. Four from Scope Boundary §5.1, three added under its own “verified dependency” exception, and the five remaining PRD §40 fields deferred because no code consumes them. The Scope Boundary governs and its exception clause is what admits the three.

E

Ownership / authorization model

Rejected by construction: no code path accepts a caller-supplied userId. No route handler, service or repository takes userId from a body, query string, path segment or header. The only producer is resolveSession(), which derives it from an httpOnly cookie via a database lookup.

How userId is obtained and bound

Request ↓ cookie: acos_session (httpOnly · Secure · SameSite=Lax) ↓ requireUser() ├─ hashAccessToken(raw) sha256 — plaintext never queried ├─ findAccessToken(hash) single indexed lookup ├─ evaluateAccessToken(stored, now) existence · revoked · expired ├─ stored.user_id IS NULL → throw entitlement token, not a session └─ → userId server-derived, unforgeable ↓ requireClientFinder(userId) users.client_finder_enabled_at IS NOT NULL ↓ service(userId, input) userId is the FIRST argument, never inside input ↓ repository.method(userId, …) every statement filters on it

How repositories enforce ownership

  • Every method takes userId as its first parameter. Positional and mandatory, so an omission is a compile error rather than a silent full-table read.
  • No method returns rows without a user_id predicate. Including single-row reads by primary key: WHERE id = $1 AND user_id = $2. An unauthorised id returns zero rows, never a row the caller then has to check.
  • Reads on child tables join to the owning row rather than trusting a denormalised column. research_signals is reached through prospects.
  • Writes set user_id from the argument, never from input data.
  • ON DELETE RESTRICT to users everywhere — matching how orders is already protected.

How worker jobs preserve ownership

The worker never receives an identity. It claims a searches row with FOR UPDATE SKIP LOCKED and reads row.user_id from persisted state. Because that row was written by an authenticated request, ownership is transitively bound to a real session without the worker knowing sessions exist. Every row it writes carries that user_id. No identity propagation, no signed job payloads, no service token — all of which would be larger surface and weaker guarantees.

How cross-user access is prevented

LayerControl
TransporthttpOnly cookie — page JavaScript cannot read or forge the session
SessionToken looked up by hash; expiry and revocation checked on every request
RouterequireUser() first in every handler. No middleware exists, so this is per-route and must be tested as such
ServiceuserId is a parameter, never part of the parsed request body
RepositoryMandatory user_id predicate on every statement
DatabaseForeign keys with ON DELETE RESTRICT; partial unique dedup scoped by user_id
TestTwo users, one dataset: B must receive empty, not A's rows and not a 500
The weakest link is the route layer, and it is worth naming. With no middleware there is no global backstop: a handler that forgets requireUser() is simply unprotected, and nothing fails. Mitigation is a standing test that enumerates route files and asserts each calls it — cheap, and the only thing that makes the omission loud.

Migration plan — 0012

Plan only. Nothing created.

Confirmed additive. Nine CREATE TABLEs, one ADD COLUMN on access_tokens, plus indexes and constraints. No ALTER to a column, no DROP, no data transformation, no backfill. Every existing row in all ten current tables is untouched.
Confirmed: does not import Client, Conversation, Activity, OutreachMessage, FollowUp or Proposal. None appears as a table, a column, a foreign key or a relation. The risk channel was opportunities, whose reused shape declares six CRM relations — all deliberately dropped. A relation is a scope decision.

  1. Prerequisite — complete C-2 steps 1–3

    Delete the root schema.prisma and pin the schema path first. migrate dev uses a shadow database that replays the chain against whichever schema the working directory resolves; doing this work while two schemas exist risks generating into the wrong file.

  2. Add users and extend access_tokens

    users with a lowercase-email CHECK; access_tokens.user_id nullable, indexed. Nullable is load-bearing: existing rows are entitlement credentials with no user, and backfilling them would invent identities.

  3. Add the seven domain tables

    service_profiles, searches, companies, prospects, research_signals, opportunities, opportunity_scores, feedback — each with user_id (or an owning parent) and ON DELETE RESTRICT.

  4. Hand-write what Prisma cannot express

    Partial unique (user_id, domain) WHERE domain IS NOT NULL; partial (prospect_id) WHERE superseded_at IS NULL; partial (requested_at) WHERE status = 'PENDING'; the CHECK constraints. Same pattern as payments_one_captured_per_order — document them in schema comments as 0001 does, since Prisma will not see them.

  5. Name it 0012_client_finder_mvp_base

    One migration, not nine — these tables have no meaning independently. Must not be backfilled into the 0005/0006 gap: those names are permanently absent from every database that ran the chain, and Prisma checks only whether a name is recorded, not whether its position is sane.

  6. Add the session secret to packages/config

    Distinct from DOWNLOAD_GRANT_SECRET — separate rotation lifetimes. Minimum 32 characters, listed in SECRET_KEYS so it is redacted and validated like the rest.

  7. Verify, then write the isolation test before the second route

    db-migrate-deploy.sh --check on a scratch database; 10 tables → 19; generated client 6 models → 15. Then the two-user isolation test. The new migration runs in every temp database across all 22 integration suites — expect a wall-clock increase and leave fileParallelism: false alone.

Open questions

■ Verified fact
  • evaluateAccessToken returns identity without reading entitlements.
  • resolveAccess returns granted: true with an empty purchased array.
  • entitlements.order_id is NOT NULL with an FK to orders.
  • reissueAccessToken gates issuance on listActive().length > 0.
  • ServiceRule requires service, triggers, keywords, typicalValuePaise, rationale.
  • suggestOffers defaults to DEFAULT_SERVICE_RULES when none is supplied.
  • access_tokens stores only the sha256 hash, with TTL and revocation.
  • Next migration number is 0012; 9 applied, none rolled back.
  • No middleware exists — authorization must be per-route.
▲ Recommended decision
  • Adopt identity ≠ entitlement ≠ payment; it is already the code's structure.
  • Extend access_tokens with nullable user_id; session = non-null.
  • users.client_finder_enabled_at as the feature boundary — not a new table.
  • Operator provisioning script; defer self-service signup and email.
  • ServiceProfile = 7 fields: 4 from §5.1 plus 3 verified dependencies.
  • Derive typicalValuePaise from minProjectValuePaise for MVP.
  • Nine tables, one additive migration 0012.
  • userId as first positional argument everywhere; never in a payload.
  • A standing test asserting every route calls requireUser().
● Unresolved — your call
  • Session lifetime. ACCESS_TOKEN_TTL_MS is 30 days, chosen for a purchased-product credential. Likely wrong for a working session; a shorter session TTL means a second constant.
  • Does typicalValuePaise deriving from the minimum read acceptably in the UI? Every opportunity's estimated value equals the user's floor.
  • Cookie name. Reuse acos_access or introduce acos_session? Separate names make the two credential kinds visible in the browser; one name is simpler.
  • Do staging or production databases exist, and at what migration state? Only the local test database was observable.
  • Feedback reason: free text or a closed set? A closed set is analysable at MVP scale; free text captures what you did not anticipate. This affects the column type.
  • Prospect vs Lead naming — recommended prospects, but it should be settled once and applied consistently.
