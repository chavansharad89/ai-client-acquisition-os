Client Finder Readiness Audit

Measured against PRD V2.0, which places the repository at Stage 6 — Client Finder MVP / Pre-Implementation. The question this audit answers is not “does the code work” but “which of the three things does it have”: implemented logic, integration, production readiness.

Implemented logic
Substantial
~294 unit tests across four acquisition-domain packages. Scoring, offers, staleness, follow-up, outreach verification, proposal versioning all present and tested.
Integrated
Almost none
Zero acquisition API routes. Zero acquisition persistence implementations. Zero integration tests touching the acquisition domain. The dashboard renders a hardcoded empty snapshot.
Production ready
No
Worker entrypoint throws. Web image cannot build. No auth. No email. Secrets validate on first request, not at boot.
01

Executive summary

The repository contains two systems. The commerce system (orders, payments, webhooks, entitlements, Meta CAPI) is genuinely built and genuinely tested: 315 integration tests run against real PostgreSQL 16.14, and the database enforces its own invariants through triggers and partial unique indexes rather than trusting application code. The acquisition system — the actual product per the PRD — is a library of pure functions with no database, no API, no worker and no user.

That split is the single most important fact in this audit, and it is consistent with the PRD's own Stage 6 declaration. It is not a defect that the acquisition engine is unfinished. It is a defect that several places in the repository describe it as further along than it is, and that the parts which do exist cannot be connected without decisions that have not been made.

Four findings would change how I'd plan the next sprint:

  1. There are two Prisma schemas and they disagree. The root schema.prisma defines the entire acquisition domain — including a User model — across 17 models. The schema the tooling actually uses, packages/db/prisma/schema.prisma, defines six. No migration creates any acq_* table. The acquisition domain has nowhere to persist to, and the file that says otherwise is not wired to anything.
  2. A refunded customer keeps the product. Verified by execution against real PostgreSQL: after a full refund, zero captured payments remain and resolveAccess still returns the entitlement. This is live revenue leakage the day real money flows.
  3. The MVP's first three stages do not exist in any form. ServiceProfile, search/discovery, candidate normalisation — zero files. The PRD's Appendix A rates these Partial; the evidence supports Not implemented.
  4. The worker cannot load its own dependencies. Every @acos/* package points main at TypeScript source, so a compiled worker importing any of them dies on SyntaxError: Unexpected token 'export'. Latent only because the entrypoint currently throws before importing anything.

Counterweight, stated plainly: the AI-evidence layer is the strongest part of the codebase. I attempted seven provenance bypasses — whitespace-padded quotes, punctuation-only quotes, real quotes cited to the wrong document, invented URLs, case shifts, paraphrases, sub-minimum lengths — and all seven were rejected.

Implemented logic

Genuinely present, tested, and matching the PRD's description. All of it is pure — no persistence, no transport. Per the PRD's own definition of IMPLEMENTED LOGIC, that is the correct bar, and these clear it.

  • Seven-factor prospect scoring with weights, bands and an explicit inference discount — core-acquisition/src/prospectScore.ts
  • Signal freshness decay with per-source-kind weighting — scoring.ts, SIGNAL_FRESH_DAYS / SOURCE_WEIGHT
  • Offer engine — offer.ts, suggestOffers()
  • Opportunity stage machine with terminal/resumable states and pause provenance — stages.ts
  • Next-action queue and staleness — nextAction.ts
  • Follow-up cadence, business-day spacing, cancel-on-reply, channel escalation — cadence.ts, followUp.ts
  • Human-approval audit trail with an actor model that refuses system actors — audit.ts, assertHumanActor
  • Outreach generation, verification, spam-phrase detection — core-outreach/src/{generator,verify}.ts
  • Proposal generation, versioning, pricing checks — core-proposal/src/{generator,versions,pricing}.ts
  • AI research with schema-validated output, targeted repair, and verbatim provenance — core-research/
  • The whole commerce path — order creation with server-side pricing, webhook trust boundary, entitlements, Meta CAPI deduplication, reconciliation.

Not implemented

Requirement is defined in PRD V2.0; no meaningful implementation exists.

  • ServiceProfile (§40) — zero files.
  • Search, async search, discovery provider, candidate normalisation, candidate deduplication (§41–45) — zero files. This is the entire FIND stage.
  • Prospect / lead persistence — no table, no repository.
  • User identity and tenancy (§39) — no userId anywhere in runtime code.
  • User feedback capture (§57) — no API, no table.
  • Conversation and qualification (§30–31) — no implementation.
  • Outcome / revenue feedback loop (§58) — metrics functions exist but nothing records outcomes.
  • AI cost management and usage metering (§59–60) — the Anthropic adapter sets max_tokens and never reads usage. No cost accounting at all.
  • PII lifecycle (§67) — webhook payload retention exists; customer PII in orders has no retention, export or erasure path.
  • Production deployment (§70) — see §23.
  • Email delivery — no transport of any kind. Breaks the PRD F-001 chain at its last step.
  • Correlation IDs / metrics / tracing — withCorrelationId throws.

Future features

Deferred by the PRD and correctly absent. Nothing in the repository speculatively implements these, which is the right call and worth noting given §107 explicitly forbids building them yet.

  • SaaS subscriptions and usage quotas (§61, Appendix A: FUTURE)
  • CRM, teams/workspaces (Appendix A: FUTURE)
  • Autonomous acquisition agents (§101 Phase 6)
  • Large-scale acquisition and scraping (§107)
  • Advanced “improve” analytics (§57)

One caveat: the root schema.prisma models acq_clients, acq_conversations and acq_activities — i.e. CRM-shaped tables — for a stage the PRD says must not be built yet. Since that schema is unused, this is latent rather than active scope creep, but it should not be migrated wholesale.

09

Critical gaps

The MVP journey has no middle. Research produces LeadResearchRow; scoring consumes ResearchSignal. The two types are shaped to line up — same kind, signal, confidence, observedAt — but no code converts one to the other, no table stores either, and no process moves data between them. Two well-built halves of a pipeline with nothing in between.
  1. No persistence for anything the product is about. Every repository implementation in the repo (createPgEntitlementRepository, createPrismaOrderRepository, createPgReconciliationRepository, createPgRateLimiter, createPgMetaEventRepository) serves commerce. ResearchRepository has zero implementations.
  2. No API surface for the product. Five routes exist: create-order, verify (501), the Razorpay webhook, and the two health probes. Nothing for service definition, search, prospects, opportunities or feedback.
  3. Refund does not revoke access — verified live (see PE-01).
  4. No identity, so no requirement that depends on “this user's” data can be satisfied.
  5. The web application cannot be built — two pages resolve to /.

B

MVP blockers

Must be resolved before the Client Finder MVP can be demonstrated end-to-end. Ordered by dependency, not severity.

  1. DB-01 — decide the authoritative schema. Nothing else in the MVP can start until there is one schema file and a migration path for acq_*. This is a decision, not an implementation, and it blocks six other items.
  2. AU-01 — identity before data. Every MVP row belongs to a user. Retrofitting tenancy after prospects exist is materially more expensive.
  3. MVP-01 — ServiceProfile. The first journey stage; the offer engine already has the parameter waiting for it.
  4. MVP-02 — FIND. Discovery provider behind an interface, candidate normalisation, dedup, prospect persistence.
  5. AI-02 / INT-01 — connect research to scoring. The table, the repository, and the assembler that turns research rows into ProspectInput.
  6. ACQ-01 — opportunity generation. The missing middle.
  7. PF-02 — feed the dashboard. One function changes.
  8. TS-01 — one end-to-end journey test against real PostgreSQL.
  9. PD-01 — resolve the route collision so a web artifact can be built at all.

PE-01, PE-02 and PD-01 are P0 for taking money, which the funnel already does. If real customers can purchase today, those three precede everything above.

C

Post-MVP

  • WK-01 / WK-02 — worker loop and package loadability. Needed for Meta attribution, not for the MVP journey itself.
  • OUT-01 — outreach wiring, and only after the send-gate migration is restored. The safety layer must be enforced before the first message can be sent.
  • PR-01 — proposals. Complete, unreachable, and correctly deferred.
  • OB-01 — correlation IDs and metrics; start by giving the logger callers.
  • AI-01 — token metering, required before any usage-based pricing.
  • PII-01 — customer PII retention and erasure.
  • SEC-04 — nonce-based CSP, using report-only violation data.
  • TS-02 — contract tests and the idempotency suite.
  • DOC-01…07, ST-01…05 — documentation and stale-artifact cleanup.

One watch item: the root schema already models acq_clients, acq_conversations and acq_activities — CRM-shaped tables for a stage the PRD forbids building. When DB-01 is resolved, migrate only what the MVP needs rather than the whole file.
