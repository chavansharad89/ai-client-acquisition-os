Identity Foundation Investigation

The MVP data model requires user ownership on every table. This establishes the smallest safe identity foundation — traced through actual execution, not inferred from filenames.

1 · Authentication status
NOT IMPLEMENTED

Not “partial”. There is no middleware, no session, no auth provider, no auth secret, no ownership check, and no authorization test anywhere in the repository. What does exist is a tested bearer-token primitive built for entitlements — valuable as a foundation, but it is not authentication and it has never been wired to an HTTP request.

▸

What tracing found

The one cookie-reading function in the repository ignores the cookie. 
// apps/web/src/server/access.ts
export async function currentAccess(): Promise<AccessResolution> {
  return ANONYMOUS;          // <- hardcoded constant, cookie never read
}
Three pages call it (/access, /access/[productId], /upsell/[productId]) and all three receive anonymous unconditionally. readAccessToken() sits directly above it with zero callers, and the acos_access cookie is never set anywhere — no cookies().set, no Set-Cookie, in any file.

This is the safe failure direction and the file says so deliberately — protected pages send visitors to checkout rather than opening up. But it means the access-control path has never executed, and no test exercises it.

A

Identity — the seven questions

1. What is the canonical user identifier?
None exists. The closest thing is orders.customer_email / entitlements.customer_email — a lowercase-constrained email used as a natural key. There is no opaque user id anywhere in the live schema.
2. Where does it originate?
The request body. customerEmail arrives in the create-order payload, validated by Zod only as a well-formed address. Nothing binds it to a verified identity.
3. How is it authenticated?
It is not. Checkout is deliberately anonymous — payment authenticity comes from the Razorpay webhook HMAC, not from the caller. That is correct for a funnel and provides nothing the MVP can build on.
4. How is it passed to application services?
As a plain function argument. createOrder(body, …) receives the parsed body; resolveAccess(repo, token) receives a raw token string. There is no request context, no async-local storage, no ctx object.
5. How is it persisted?
As a denormalised email column on orders, entitlements and access_tokens, each with a lower() CHECK constraint. No foreign key to any identity table, because none exists.
6. How is ownership enforced?
It is not enforced anywhere. Grep across every route and every repository returns no ownership predicate. Entitlement checks are entitlement checks (does this email own this product), not tenancy checks.
7. Can one user access another user's data?
The question does not yet apply — and that is the risk. No user-owned data exists, so there is nothing to cross. The moment the MVP tables land, every one of them will need a predicate that the codebase has never written once. There is no existing pattern to copy and no test to imitate.

C

API authorization — traced

The only state-changing request in the repository, traced end to end:

POST /api/payments/create-order ↓ NO authentication step — no middleware, no session lookup ↓ clientIpOf(request) ← x-forwarded-for, caller-controlled ↓ request.json() ← body ↓ createOrderRequestSchema.safeParse(body).strict() ↓ customerEmail ← CALLER-SUPPLIED, unverified ↓ createOrder(body, config, { razorpay, orders }) ↓ createPrismaOrderRepository(prisma) ↓ INSERT INTO orders (customer_email, …) no ownership predicate

Is userId guaranteed rather than caller-supplied?

Neither. There is no userId in the request path at all. The identity-shaped value that does flow — customerEmail — is caller-supplied with no server-side binding whatsoever.

This is not currently a vulnerability, and it will become one. For anonymous checkout, a self-declared email is correct: you are naming where the product should be delivered, and money is verified by webhook signature rather than by the claim. But it means the repository contains no example of server-bound identity. The MVP will introduce the first one, so the pattern must be established deliberately rather than copied.

D

Worker ownership

The existing worker has a workerId, and it is worth being precise about what that is: a process identity used for lease fencing — proving which worker holds a row — not a user identity. The claim statement has no ownership predicate; it takes any due row.

The existing pattern is already the safe one, and it generalises. The worker never receives identity from a caller. It reads a persisted row, and everything it needs comes from that row. Applied to search:
HTTP POST /api/searches ↓ authenticate → userId (server-derived, never from the body) ↓ INSERT searches (user_id = userId, status = 'PENDING') ↓ respond 202 + searchId WORKER claim: SELECT … WHERE status='PENDING' … FOR UPDATE SKIP LOCKED ↓ userId := row.user_id (read from persisted state) ↓ every write carries that user_id ↓ companies / prospects / research / opportunities / scores

The rule to encode: the worker derives ownership from the row it claimed, never from job payload it was handed. Because the row was written by an authenticated request, ownership is transitively bound to a real session without the worker knowing anything about sessions. No identity propagation, no signed job payloads, no token passed to the worker — all of which would be larger and weaker.

One consequence worth deciding now: if a user is deleted while a search is running, the worker will write rows for an owner that no longer exists. A foreign key with ON DELETE RESTRICT — matching how orders is already protected — makes that a loud failure rather than orphaned data.

Where Company fits — and the shared-vs-owned decision

The user asked for this to be decided explicitly against deduplication and multi-user isolation. The two pull in opposite directions.

Globally shared CompanyUser-owned Company
DeduplicationOne row per real business; strongest dedupDedup scoped per user; the same restaurant may exist twice across two users
Research costResearch reusable across users — cheaper at scaleResearch repeated per user — more model spend
IsolationLeaks — row existence, timestamps and research reveal what other users are pursuingClean — every row has one owner
Erasure / PIIHard — a shared row cannot be deleted with one userSimple — delete by user_id
ConsentRequires deciding whether A's research may serve BNo question arises
Query shapeEvery read needs a join to prove entitlement to the rowEvery read filters on one column
Recommendation: user-owned for the MVP. Four reasons, in order of weight:
  1. Isolation is an exit criterion; cost efficiency is not. Sharing trades the thing being validated for an optimisation that only matters at a scale the MVP will not reach.
  2. The MVP dedup requirement is per-user — “one business appears to the user once” (Scope Boundary §3 stage 4). Global uniqueness is a stronger guarantee than anything asked for.
  3. Sharing raises a consent question the MVP should not answer: may one user's research serve another? That is a product and privacy decision, not a schema detail.
  4. Reversibility. Going user-owned → shared later is a deduplicating backfill. Going shared → user-owned later means splitting rows whose provenance has already been merged. The cheap mistake is the reversible one.

Concretely: Company carries user_id, with a partial unique index on (user_id, domain) WHERE domain IS NOT NULL as the dedup key. Prisma cannot express a partial unique index, so it goes in hand-written SQL — the same treatment payments_one_captured_per_order already receives.

Identity architecture

What can be reused, and what must be built

■ Already built and tested
  • access_tokens table — opaque token, only the sha256 hash stored, TTL, revoked_at, last_used_at
  • mintAccessToken() — 32 bytes of CSPRNG, base64url
  • hashAccessToken() and a timing-safe comparison
  • reissueAccessToken() — magic-link issuance with an enumeration-safe identical refusal
  • REISSUE_EMAIL_POLICY (3/15min) and REISSUE_IP_POLICY (10/15min)
  • createPgRateLimiter — shared counters across replicas
  • ACCESS_COOKIE name and the httpOnly intent
  • HMAC signed-capability pattern in downloadGrant.ts — a worked example of layered checks
  • Env validation with secret-name redaction in packages/config
▲ Missing
  • A users table and an opaque user id
  • user_id on access_tokens (it is email-scoped today)
  • Cookie issuance — nothing sets a cookie anywhere
  • A verification step in the request path — currentAccess() returns a constant
  • A request-context mechanism to carry userId into services
  • An ownership predicate — the codebase has never written one
  • An auth secret in config, distinct from DOWNLOAD_GRANT_SECRET
  • Email transport — blocks magic-link login entirely
  • Any authorization test

Recommended minimum architecture

The existing token system is an entitlement bearer credential keyed on email, not an identity system: issuance is gated on listActive() returning purchases, and there is no user concept. It is nonetheless the right foundation, because the hard parts — hash-only storage, TTL, revocation, timing-safe comparison, rate-limited issuance, enumeration safety — are built and tested.

Extend it; do not build a second credential store.
  1. Add a users table: id, email (unique, lowercase CHECK), name, created_at, updated_at.
  2. Add a nullable user_id to access_tokens, with an index. Existing rows keep user_id IS NULL and remain entitlement credentials.
  3. Session = a token row with a non-null user_id. Same mint, same hash-only storage, same revocation — one mechanism, two purposes, distinguished by a column.
  4. Add a server-only requireUser() helper that reads the cookie, looks up the hash, checks expiry and revocation, and returns userId — or throws. Every MVP route calls it first and takes userId from nowhere else.
  5. Every MVP repository method takes userId as its first argument and filters on it. No method accepts an unfiltered read.
Login is blocked by a dependency outside this investigation. Magic-link is the natural mechanism — the issuance, rate-limiting and enumeration-safety are already written — but there is no email transport in the repository (audit PE-02). Two ways forward, and this needs a decision:
  • (a) Implement email transport first, then self-service magic-link login. Larger, and unblocks paid-product delivery too.
  • (b) Provision the handful of MVP validation users out of band — a seeding script issuing a token directly — and defer self-service signup. The controlled scenario (one service, one city, restaurants) implies a small, known set of validators.
(b) is the smaller safe foundation and is what “minimum required for the MVP” points at. It keeps the same session mechanism, so (a) later adds a login route and changes nothing else.

Deliberately excluded: passwords, OAuth, MFA, refresh-token rotation, roles and permissions, workspaces, tenant hierarchies, and device management. None is required by any exit criterion, and PRD §39 places workspace/tenant behind production SaaS.

Migration plan

Sequence only. Nothing executed, nothing created.

  1. Decide the two open questions in section 6

    Login mechanism (a or b) and Company ownership. Both change the DDL, so both precede any schema edit.

  2. Complete C-2 steps 1–3 first

    Delete the root schema.prisma and pin the schema path. Doing identity work while two schemas resolve by working directory risks writing models into the wrong file — and the shadow database replays whichever one is found.

  3. Add the identity models to the authoritative schema

    users, plus nullable user_id on access_tokens. Nothing else in this step.

  4. Add the seven MVP domain models

    ServiceProfile, Search, Company, Prospect, ResearchSignal, Opportunity, OpportunityScore, Feedback — each with user_id and ON DELETE RESTRICT to users.

  5. Author 0012_client_finder_mvp_base

    One additive migration. Hand-written SQL for what Prisma cannot express: the partial unique index on (user_id, domain), and the lowercase CHECK on users.email matching the convention in 0004.

  6. Add an auth secret to packages/config

    Distinct from DOWNLOAD_GRANT_SECRET, minimum 32 characters, listed in SECRET_KEYS so it is redacted and boot-validated like the rest.

  7. Implement requireUser() and one protected route

    One route establishes the pattern every other copies. Do not build nine routes before proving one.

  8. Write the isolation test before the second route

    Two users, one dataset: user B must receive empty, not user A's rows — and not a 500. This is the test that makes AZ-1 and AZ-2 stop being risks.

  9. Verify the chain and the suite

    db-migrate-deploy.sh --check on a scratch database; then the full pipeline. The new migration runs in every temp database across all 22 integration suites.

Decisions requiring approval

■ Verified facts
  • No middleware, auth provider, JWT/session library, or auth secret exists.
  • currentAccess() returns a hardcoded constant; the cookie is never read or set.
  • readAccessToken() has zero callers.
  • No ownership predicate exists in any route or repository.
  • No authorization test exists; all 401s are webhook signature checks.
  • The live database has 11 tables and no identity table.
  • access_tokens is keyed on customer_email with no user_id.
  • The only User model is in the root schema C-2 recommends deleting, and has no credential fields.
  • customerEmail is caller-supplied with no server-side binding.
  • workerId is a lease-fencing process identity, not a user identity.
  • Next valid migration number is 0012; 9 applied, none rolled back.
  • No email transport exists anywhere in the repository.
▲ Recommended
  • Status is NOT IMPLEMENTED, not partial.
  • Extend access_tokens with user_id rather than building a second credential store.
  • Opaque users.id as the ownership anchor — never email as a foreign key.
  • Company is user-owned, with a partial unique index on (user_id, domain).
  • Worker derives ownership from the claimed row, never from a job payload.
  • ON DELETE RESTRICT to users on every MVP table.
  • A separate auth secret; do not reuse DOWNLOAD_GRANT_SECRET.
  • Out-of-band user provisioning for MVP validation; defer self-service signup.
  • requireUser() per route, since there is no middleware backstop.
  • Write the two-user isolation test before the second protected route.
● Unresolved — needs your decision
  • Login mechanism: implement email transport for magic-link (a), or provision validation users out of band (b)? This gates the DDL.
  • Is the Client Finder MVP gated behind the ₹1,499 purchase? If yes, identity and entitlement converge and access_tokens needs far less change. If no, they must stay separate. Nothing in the repository answers this.
  • ServiceProfile field set: PRD §40 lists 13 fields; Scope Boundary §5.1 requires 4. Recommend the 4 — but that is a scope conflict between two governing documents.
  • Do staging or production databases exist, and at what migration state? Only the local test database was observable.
  • Session lifetime. ACCESS_TOKEN_TTL_MS is 30 days, chosen for a purchased-product credential. That may be wrong for a working session.
  • Prospect vs Lead naming. The PRD journey says prospect; the existing shape says Lead. Cosmetic, but it should be settled once.
