Final Schema Design Review

Remaining model and field ambiguities resolved before migration 0012. This review changes three things from the prior Foundation Design — each because inspecting the consuming code contradicted the earlier assumption.

Correction 1
typicalValuePaise removed entirely
It is a second pricing concept the MVP never displays. Estimated value is not in Scope Boundary §5.4. Derived at adapter time, persisted nowhere.
Correction 2
Evidence must persist its classification
The existing mapper folds OBSERVED/INFERRED into confidence and drops UNKNOWN rows. That makes a stated MVP capability unimplementable and risks discounting inference twice.
Correction 3
Search snapshots its parameters
Reading them live from ServiceProfile would let an edit retroactively rewrite what a past search searched for — and make its explanations false.

2

Access tokens — minimum change

ALTER TABLE access_tokens ADD COLUMN user_id TEXT NULL REFERENCES users(id) ON DELETE RESTRICT; CREATE INDEX access_tokens_user_id_idx ON access_tokens(user_id) WHERE user_id IS NOT NULL;

One nullable column and one partial index. Nothing else: not the hash, not the TTL, not revoked_at, not last_used_at, not the lowercase-email CHECK.

Row kinduser_idMeaningResolved byGrants
Legacy / entitlementNULLBearer credential for a purchased product, keyed on customer_emailresolveAccess()Product access only
SessionsetAn authenticated user sessionresolveSession()Identity only
Legacy rows behave exactly as they do today. resolveAccess() is unchanged — it looks a token up by hash, evaluates expiry and revocation, and reads customer_email. It never consults user_id, so a NULL is invisible to it. No backfill: existing tokens have no user, and inventing one would fabricate identity.
The two kinds must not be interchangeable, and one line enforces it. requireUser() rejects a token whose user_id IS NULL — otherwise an entitlement token emailed to a customer would authenticate as a Client Finder session. Without that check the separation established in Decision 1 collapses at the first route.

Payment semantics untouched: no change to orders, payments, entitlements, or any trigger on them.

Why the rule fields are configuration, yet still persisted

triggers is a list of ResearchSignal['kind'] enum values — JOB_POST, FUNDING, TECH_STACK. Asking a freelancer to choose those is asking them to understand the scorer's internals, so they are not user profile data and must not appear as form fields.

They are nonetheless persisted, for the same reason scorer_version is persisted: an opportunity shows why it was selected, and that explanation must remain true after the derivation logic changes. Recomputing rules at read time would silently rewrite the history of past searches.

ServiceRule is assembled from the profile, not stored as a rule table. An adapter reads the four user fields plus the three derived fields and constructs ServiceRule for suggestOffers(). No service_rules table: the relationship is 1:1 at MVP scale, and a table for a 1:1 is indirection without benefit.

Does typicalValuePaise duplicate minProjectValuePaise?

Semantically no; practically yes — so it is removed.
  • They mean different things: typical is what an engagement is worth; minimum is the user's floor for bothering.
  • But ServiceRule.typicalValuePaise exists only to populate an offer's value, which populates Opportunity.estimatedValuePaise — and estimated value is not in Scope Boundary §5.4. The MVP displays evidence, score, rank, next action and offer. Not money.
  • Persisting it would ask the user for a number the MVP never shows, or derive it from the minimum and display the floor as an estimate — which is worse than showing nothing.
Resolution: the adapter supplies typicalValuePaise := minProjectValuePaise to satisfy the interface, the resulting value is not persisted, and opportunities.estimated_value_paise is dropped from the MVP model. One pricing concept, not two — which is what §15's duplicate-pricing check asks for.

Company vs Prospect ownership

GuaranteeA · Company.userIdB · Company global
No cross-user visibilityDirect — one predicateIndirect — must always join via Prospect; a direct Company read leaks row existence
Per-user deduplicationNative — partial unique on (user_id, domain)Native — global unique on domain

Migration path preservedYes — mechanical mergeOne-way — splitting merged rows is not mechanical

ErasureDelete by user_idA shared row cannot be deleted with one user
Recommendation: A — Company is user-owned. Not because it is simpler. The decisive argument is that the MVP is validating deduplication itself: normalize and deduplicate are journey stages 3 and 4, and whether domain is a reliable identity key is one of the things the experiment answers. Committing to a global identity namespace before that answer is known bakes in a guess, and a wrong dedup rule in a shared namespace corrupts every user's data at once rather than one user's.

Two design choices keep option B reachable:

  • Persist normalized_domain explicitly rather than normalising at query time. A future global merge needs a deterministic join key that was computed the same way for every row.
  • Keep Company minimal. The more descriptive fields it carries, the more conflicts a future merge has to resolve. Anything user-specific belongs on Prospect.

5

Search

Snapshot, not dynamic read. If the worker read parameters live from service_profiles, editing a profile would retroactively change what a completed search searched for — and every opportunity's stored rationale would describe criteria that were never used. Historical reproducibility requires the inputs to be frozen with the run, exactly as scorer_version freezes the scoring logic.
searches id TEXT PK user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT service_profile_id TEXT NOT NULL REFERENCES service_profiles(id) ON DELETE RESTRICT parameters JSONB NOT NULL -- frozen snapshot, see below status TEXT NOT NULL -- PENDING RUNNING COMPLETE FAILED CANCELLED requested_count INTEGER NOT NULL DEFAULT 20 idempotency_key TEXT NULL UNIQUE attempts INTEGER NOT NULL DEFAULT 0 last_error TEXT NULL lease_owner TEXT NULL lease_expires_at TIMESTAMP(3) NULL requested_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP started_at TIMESTAMP(3) NULL finished_at TIMESTAMP(3) NULL created_at / updated_at INDEX (user_id, requested_at DESC) INDEX (requested_at) WHERE status = 'PENDING' -- claim query; mirrors meta_events_due_idx

parameters holds the seven ServiceProfile values in use at creation time — service, targetCustomer, geography, minProjectValuePaise, signalTriggers, keywords, offerRationale. JSONB rather than seven columns because the worker reads it as a unit and nothing queries across it at MVP scale; service_profile_id is retained separately for lineage.

Result relationship: prospects.search_id → searches.id. Opportunities reach a search transitively through their prospect; no direct search_id on opportunities, which would be a second path to the same fact and could disagree with the first.

Prospect

prospects id TEXT PK user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT search_id TEXT NOT NULL REFERENCES searches(id) ON DELETE RESTRICT company_id TEXT NOT NULL REFERENCES companies(id) ON DELETE RESTRICT source TEXT NOT NULL -- discovery provenance: which provider returned it source_ref TEXT NULL -- the provider's own id, for re-fetch and debugging full_name TEXT NULL email TEXT NULL role TEXT NULL linkedin_url TEXT NULL status TEXT NOT NULL -- DISCOVERED RESEARCHED SCORED REJECTED unsubscribed_at TIMESTAMP(3) NULL created_at / updated_at UNIQUE (search_id, company_id) INDEX (user_id) · INDEX (company_id)
UNIQUE(search_id, company_id), not (user_id, company_id). Within one search a business must appear once — that is the deduplication requirement. Across searches it should be allowed to reappear: a user searching again in three months wants the same restaurant re-surfaced with fresh research, and a user-scoped constraint would silently suppress it.

Discovery provenance is source + source_ref on the prospect rather than on the company, because provenance is a fact about this discovery event, not about the business. It also survives the future move to a shared Company table unchanged.

unsubscribed_at is carried because ProspectInput.contact.unsubscribed is a hard stop in the existing scorer — it overrides every other factor. Nothing in the MVP sets it; it exists so the scorer's contract can be satisfied honestly rather than by hardcoding false.

7

Research signal / evidence

The existing mapper cannot satisfy the MVP's stated requirements. toResearchRows() in core-research/src/persist.ts: 
.filter((o) => o.classification !== 'UNKNOWN')     // UNKNOWN rows are DISCARDED
  confidence: effectiveConfidence(observation)      // OBSERVED/INFERRED folded into a number
  sourceUrl: observation.evidence[0]?.sourceUrl     // only the FIRST of up to 5 sources
  weight: 0                                          // placeholder
Three consequences: the UI cannot display observed / inferred / unknown (Scope Boundary §5.3), it cannot show more than one source (§5.6 evidence display), and — because effectiveConfidence already halves INFERRED while the scorer's INFERENCE_DISCOUNT = 0.5 halves it again by basis — inference can be discounted twice.
research_signals id TEXT PK prospect_id TEXT NOT NULL REFERENCES prospects(id) ON DELETE RESTRICT company_id TEXT NOT NULL REFERENCES companies(id) ON DELETE RESTRICT field TEXT NOT NULL -- which observation produced it kind TEXT NOT NULL -- WEBSITE JOB_POST LINKEDIN NEWS FUNDING TECH_STACK REVIEW MANUAL classification TEXT NOT NULL -- OBSERVED | INFERRED | UNKNOWN <-- restored signal TEXT NULL -- NULL permitted for UNKNOWN confidence INTEGER NOT NULL -- RAW, unadjusted; CHECK 0..100 source_url TEXT NULL source_quote TEXT NULL -- the verbatim span provenance already verifies observed_at TIMESTAMP(3) NOT NULL superseded_at TIMESTAMP(3) NULL created_at INDEX (prospect_id) WHERE superseded_at IS NULL -- the scorer reads live signals only
Store raw confidence; discount once, at scoring time. The persisted row keeps classification and the unadjusted confidence. The adapter supplies basis to the scorer, which applies INFERENCE_DISCOUNT — the single place a discount is applied. This also makes the row honest: a stored 80 means the source asserted 80, not 80-after-a-halving-someone-has-to-remember.

UNKNOWN rows are kept, with signal NULL. They are what lets the UI say “we could not establish ability to pay” instead of silently omitting a factor — and the scorer already has an UNKNOWN basis that contributes zero. Freshness needs no column: observed_at plus the existing decayFactor() computes it. Supersession is an UPDATE of superseded_at, never a delete.

Not a knowledge graph: no entities, no relations, no triples. One flat append-only table whose columns map one-to-one onto what ProspectInput.signals consumes.

Feedback

feedback id TEXT PK user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT opportunity_id TEXT NOT NULL REFERENCES opportunities(id) ON DELETE RESTRICT useful BOOLEAN NOT NULL reason TEXT NULL created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP updated_at TIMESTAMP(3) NOT NULL UNIQUE (user_id, opportunity_id) INDEX (opportunity_id)
Can this grow into outcome/revenue learning without importing future analytics? Yes — and the shape is what makes it possible. Feedback keyed on (user_id, opportunity_id) is already the join key every later outcome question needs: did you contact them, did they reply, did you win. Each is a future nullable column or a sibling table keyed the same way. None is added now — the MVP asks one question, “would you actually contact this business?”, and Scope Boundary §9 places the rest in outcome validation that may extend beyond this implementation.

reason free text rather than a closed set — the MVP is discovering why opportunities are rejected, and a premature enum would record only the reasons that were already guessed. This remains an open question in §15 if analysability is preferred.

Two models deliberately carry no user_id. research_signals and opportunity_scores are leaf tables reached only through an owned parent, so a denormalised owner would be a second source of truth that can disagree with the first. Denormalise later only if a measured query plan demands it — and then with a constraint keeping the two in step.

Cross-user test requirement

One test per owned model, all the same shape: seed user A, authenticate as user B, request A's row by its primary key. B must receive an empty result — not a 403, not a 500, and certainly not the row. Empty is the correct answer because it also avoids confirming that the id exists.

Worker ownership

HTTP POST /api/searches requireUser() → userId server-derived from the session cookie INSERT searches (user_id = userId, parameters = snapshot, status='PENDING') WORKER claim: UPDATE searches SET status='RUNNING', lease_owner=$worker, lease_expires_at=now()+lease WHERE id IN (SELECT id FROM searches WHERE status='PENDING' AND requested_at <= now() ORDER BY requested_at FOR UPDATE SKIP LOCKED LIMIT $n) RETURNING id, user_id, parameters userId := row.user_id read from persisted state, never from a payload params := row.parameters frozen at creation, not re-read from the profile every INSERT it makes carries that user_id: companies · prospects · research_signals · opportunities · opportunity_scores settle: fenced UPDATE … WHERE id=$1 AND lease_owner=$worker
The worker has no job payload, so there is nothing to forge. It is handed nothing; it claims a row and reads ownership out of it. Because that row could only have been written by a request that passed requireUser(), ownership is transitively bound to a real session without the worker knowing sessions exist. This is the pattern the meta_events worker already uses and is the only worker component proven against real PostgreSQL.

The lease_owner fence matters for the same reason it does in meta_events: a worker whose lease expired mid-run must not overwrite the row a new worker now holds. Settle statements carry AND lease_owner = $worker.

Final approval check

  • No future CRM capability entered MVP — six models excluded as tables and as relations; the opportunities back door closed explicitly.
  • No subscription system entered MVP — no plan, quota, billing-period or usage-meter column anywhere.
  • No autonomous outreach entered MVP — no message, channel, send-state or schedule column. unsubscribed_at is a scorer input, not an outreach capability.
  • No proposal system entered MVP — no proposal table, no version, no pricing block.
  • No unnecessary authentication infrastructure entered MVP — one nullable column on an existing table. No sessions table, no password, no OAuth, no MFA, no roles, no workspaces.
  • No duplicate service-pricing concepts — typicalValuePaise removed and estimated_value_paise dropped. min_project_value_paise is the single pricing concept.
  • No cross-user access path exists by design — every owned model filters on user_id; the two leaf tables reach it through a join; no route, service or repository accepts a caller-supplied userId.
  • Schema is compatible with existing architecture — TEXT uuid keys, TIMESTAMP(3), created_at/updated_at, lowercase-email CHECKs, ON DELETE RESTRICT, partial indexes in hand-written SQL. Every convention matches migrations 0001–0011.
  • Migration 0012 can be additive — confirmed against all eight criteria in §13.
  • One caveat: toResearchRows() as written cannot populate research_signals — it discards classification and UNKNOWN rows. The adapter must map observations directly, or that function must be extended. This is implementation work, not a schema change, but it must not be discovered mid-build.
■ Verified fact
  • toResearchRows filters out UNKNOWN and folds classification into confidence via effectiveConfidence.
  • effectiveConfidence halves INFERRED; the scorer's INFERENCE_DISCOUNT also halves by basis.
  • ServiceRule requires service, triggers, keywords, typicalValuePaise, rationale.
  • ProspectScore returns score, band, factors[], reasons[], observedShare, cap?.
  • Seven factors; weights sum to 100, asserted by an existing test.
  • FactorScore carries factor, weight, raw, points, basis, reason.
  • ProspectInput.contact.unsubscribed is a hard stop overriding all factors.
  • entitlements.order_id is NOT NULL; access_tokens has no user_id.
  • Next migration number is 0012; 9 applied, none rolled back.
▲ Recommended decision
  • Remove typicalValuePaise; drop estimated_value_paise.
  • Persist classification and raw confidence; discount once, at scoring time.
  • Keep UNKNOWN signals with a NULL signal value.
  • Snapshot search parameters as JSONB at creation.
  • Company user-owned, with normalized_domain preserved as the future merge key.
  • UNIQUE(search_id, company_id), not (user_id, company_id).
  • UNIQUE(prospect_id) on opportunities — one offer per prospect for MVP.
  • No user_id on research_signals or opportunity_scores.
  • requireUser() rejects tokens where user_id IS NULL.
  • No email verification column for MVP.
● Open question
  • Session TTL. ACCESS_TOKEN_TTL_MS is 30 days, chosen for a purchased-product credential. A working session likely wants less — that means a second constant.
  • Feedback reason: free text or closed set? Recommended free text; a closed set is more analysable but records only anticipated reasons. Affects the column type.
  • Cookie name — reuse acos_access or add acos_session? Separate names make the two credential kinds visible; one name is simpler.
  • Who derives signal_triggers/keywords/offer_rationale? A curated catalogue matched on the service string, or an AI pass over the profile text. Changes the profile-creation path, not the schema.
  • Prospect status values. Proposed DISCOVERED/RESEARCHED/SCORED/REJECTED; not specified by the PRD, which defines stages only for Opportunity.
  • Do staging or production databases exist, and at what migration state? Only the local test database was observable.
