Database Authority Decision

Two Prisma schemas disagree and no migration creates the acq_* tables. This determines which schema is authoritative, on evidence rather than model count — and finds that neither schema currently describes the Client Finder MVP.

A · Database authority decision
packages/db/prisma/schema.prisma

It is already authoritative in every operational sense. The root schema.prisma is not a competing candidate — it is an inconsistent snapshot that is wrong about the models it shares.

PROOF 1
It generated the client
The generated client contains exactly its 6 models and carries the linux-musl query engines that only this schema declares via binaryTargets. The root schema has no such block.
PROOF 2
It matches the live database
On all three disputed columns. The root schema is missing idempotencyKey, and declares customerName required where the database has it nullable.
PROOF 3
It owns the applied history
Nine migrations recorded in _prisma_migrations, none rolled back, all resolving to this schema's directory. The root schema has no migrations directory at all.
!

The hazard this investigation found

Prisma's schema resolution is working-directory dependent, and both schemas are individually valid. Verified by execution: 
$ cd packages/db && prisma validate
Prisma schema loaded from prisma/schema.prisma      # 6 models

$ cd <repo root> && prisma validate
Prisma schema loaded from schema.prisma             # 17 models
The root schema is not dormant. Any bare prisma command run from the repository root loads it. Because ./migrations/ does not exist, a prisma migrate dev from the root would create a second migration history alongside the real one, generating DDL for eleven unreviewed models — including CRM tables the MVP Scope Boundary explicitly defers.

This reclassifies the root schema from “stale artifact” (as the Readiness Audit recorded it) to an active footgun. It is the single strongest argument for removing it rather than leaving it in place as reference material.

A third representation exists and agrees with neither. The quarantined migrations describe an acquisition schema that the root Prisma file does not match:
  • 0005 adds twelve columns to acq_outreach_messages (approval_state, approved_by, prompt_version, evidence_used, …). None appears in the root schema's OutreachMessage.

C

MVP database model

Neither existing schema covers the MVP. Four of the models the Client Finder journey requires — ServiceProfile, Search, an opportunity score record, and Feedback — appear in no schema and no migration anywhere in the repository. The root schema is not a shortcut to the MVP; it is a different product's data model.

Minimum set for the journey in MVP_SCOPE_BOUNDARY.md §3. Nine models. New means no definition exists anywhere; Adapt means the root schema has a usable shape to copy from, stripped of deferred relations.

UserAdapt
Tenancy anchor. Every MVP row hangs off this. The root schema's model is a record of a user, not an auth mechanism — it carries no credential, provider or session field, so the authentication decision is still open and is not resolved by adopting it.
id · email (unique) · name · createdAt · updatedAt

D

Migration plan

Described only. No migration created.

  1. Remove the root schema.prisma

    Delete it, or move it to requirement/reference/ with a non-.prisma extension so no CLI can load it. Leaving it in place preserves the root-CWD hazard. Its useful content — the LeadResearch, Company, Lead and User shapes — is captured in section C above and does not need the file to survive. Update the one prose reference in infra/migrations-runbook.md.

  2. Pin the schema path so resolution can never drift

    Add a "prisma": { "schema": "prisma/schema.prisma" } block to packages/db/package.json, and keep the explicit --schema flag in scripts/db-migrate-deploy.sh. After step 1 there is only one schema; this stops a second from being introduced silently.

  3. Add the nine MVP models to packages/db/prisma/schema.prisma

    Section C, and nothing else. The six deferred models stay out. Prisma cannot express two constraints the MVP needs — a partial unique index for per-user company deduplication, and any CHECK — so those go in hand-written SQL, consistent with how payments_one_captured_per_order is already handled.

  4. Generate one migration, numbered 0012

    It must not be backfilled into the 0005/0006 gap. Those numbers are permanently absent from _prisma_migrations on every database that has run the chain. A new migration sorting before nine already-applied ones would apply out of order on existing databases — Prisma checks only whether a name is recorded, not whether its position is sane.

    Name it for what it is, e.g. 0012_client_finder_mvp_base. One migration, not nine: these tables have no meaning independently, and a single reviewable unit is easier to reason about than a sequence that leaves the schema incoherent midway.

  5. Leave migrations-blocked/ untouched

    Restoring 0005/0006 is not part of this work. They target acq_outreach_messages and acq_opportunities — outreach tables the MVP defers. Their base schema still will not exist after step 4, which is correct. Note for Phase 2: 0006 assumes a pre-existing OpportunityStage enum with four values the MVP will not create, so it cannot be restored as written even once outreach is in scope.

  6. Regenerate the client and verify drift is zero

    pnpm db:generate, then scripts/db-migrate-deploy.sh --check against a fresh database. The generated client should go from 6 models to 15.

  7. Confirm the existing suite still passes

    The new migration runs inside every temporary database created by all 22 integration suites. Expect a wall-clock increase and watch for connection pressure — fileParallelism is already disabled for that reason. The pipeline policy test will independently verify that no migration ALTERs a table the chain never creates.

F

Recommendation

One recommended architecture, with the evidence and the judgment kept separate.

■ Verified repository facts
  • packages/db/prisma/schema.prisma generated the current client (6 models, musl engines).
  • It matches the live database on all three disputed columns; the root schema does not.
  • Nine migrations are applied, none rolled back; numbering gaps at 0005/0006.
  • Prisma resolves by CWD; both schemas validate; ./migrations/ does not exist.
  • The root schema conflicts with the database on Order.idempotencyKey, Order.customerName and WebhookEvent.payloadRedactedAt.
  • It is post-0006 for OpportunityStage and pre-0005 for outreach columns.
  • It contains no ServiceProfile, Search, score or Feedback model.
  • Its LeadResearch is a superset of LeadResearchRow in core-research.
  • Prisma is used at 3 sites; raw pg at 15; no test imports PrismaClient.
  • No package imports Prisma-generated types.
  • db-migrate-deploy.sh already pins --schema explicitly.
▲ Architectural recommendation
  • Make packages/db/prisma/schema.prisma authoritative de jure, as it already is de facto.
  • Delete the root schema rather than relocating it — relocation leaves the CWD hazard if the extension is kept.
  • Add exactly the nine models in section C. Defer the other six.
  • One additive migration, 0012 or higher.
  • Keep Prisma as the schema and migration tool; do not adopt it as the acquisition query layer. The repository has already chosen raw SQL 15 times to 3, and core-payments deliberately avoids Prisma types.
  • Write acquisition repositories against pg, matching createPgEntitlementRepository and createPgMetaEventRepository.
  • Resolve authentication before step 3 — User carries no credential field, so adopting it does not decide the auth mechanism, and every MVP table takes a userId.
Why not the root schema, despite having more models. Not because it is larger or smaller, but because it is wrong: it contradicts the live database on three columns, represents no coherent point in the migration history, describes eleven tables no migration creates, omits four models the MVP needs, and includes six the Scope Boundary defers. Adopting it would import CRM into a release that excludes CRM — and a schema decision expands scope as effectively as a feature does.
